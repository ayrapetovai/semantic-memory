# Генеративная Rogue-игра с LLM — решения по архитектуре (2026-11-15)

- Архитектура: механика обеспечивается классическим детерминированным кодом (Rogue-сетка, движение, FOV, бой, инвентарь, RNG по seedу, сохранение), LLM — только нарративный слой и актёр врагов; LLM не владеет состоянием мира.
- База атомарных фактов = единственный источник истины: типизированные записи с id (faction, room, prop, quest); сюжет — цепочка фактов → квестовый граф, который исполняет код. Память сюжета в БД, не в контексте модели.
- Комната и враг генерируются лениво при входе в дверь: layout — процедурный генератор по seedу, содержимое — LLM из цепочки фактов; валидатор проверяет проходимость врага, диапазон урона, существование выхода.
- Враг: тактика (pathfinding, выбор удара) — код, реплика/намерение — LLM; модель объявляет `{intent}`, бой разрешает код. Союзник — реальная сущность со своим AI и записью в фактах, не текст в диалоге.
- Конструктор магии: грамматика примитивов (эффект, цель, стоимость, модификаторы) + whitelist; LLM собирает заклинание из whitelist в JSON, код валидирует и исполняет — баланс остаётся у кода.
- Шаблоны планов как данные, не код: building (partition комнат 3..7, коридор width 1), castle (keep + courtyard + внешняя стена, башни по углам), cave (blob cellular-automata, тупиковые ветки, без окон), forest (поляны-узлы + пути-рёбра, деревья как obstacle density по noise).
- Генерация плана в 4 прохода: скелет-граф зон → планировка (прямоугольники комнат, коридоры между door'ами) → расстановка props → валидация; при провале валидатора seed меняется и проход повторяется.
- Правила расстановки: окно только на внешней стене (выводится из partition), стол у стены, стул напротив стола, сундук в углу/нише и никогда в коридоре, дверь соединяет ровно 2 зоны и стоит в стене, мебель не ставится в коридоре.
- Предметы — сущности с id и коллизией: стол/шкаф блокируют движение, сундук — контейнер с содержимым из фактов, окно непроходимо или открываемое; layout и props пишутся в факты, иначе сейв не воспроизведёт ту же планировку.
- Один grid → два рендера: пиксельный (тайлы 32×32, атлас на биом + палитра, стены в 2 строки) и schematic-план (прямоугольники комнат + разрывы дверей); статичные тайлы комнаты кешируются в одну текстуру, динамические рисуются отдельно.
- Стиль Vulture for NetHack = изометрия, не план сверху: DanielT/Vulture (архив, NetHack 3.4.3), dembobbys/vultures (NetHack/Slash'EM), HackTechDev/Vulture4Nethack (2020), активно поддерживаемый copperwater/xNetHack (NetHack 3.7-dev). Свой тайловый лист в сетке 32×32 даёт тот же вид без чужих ассетов; листы NetHack требуют атрибуции по своей лицензии.
- ISA примитивных команд как ассемблерные строки: `push e12 n 3`, `take chest.c5`, `say goblin "…"` — одна строка = одна дельта состояния; LLM = ассемблер, код = VM. Формат строк дешевле JSON и парсер копеечный.
- Правила ISA: ортогональные примитивы, типизированные операнды (id, направление, координаты, количество, сила), детерминизм, цена хода/AP, лимит 3 команды за ход, глубина цепочек эффектов 2, без control flow в программе.
- Ядро взаимодействия вместо отдельной механики боя: у всего на сетке есть масса, устойчивость, трение, проходимость, террейн; толчок = displacement → смещение на N клеток или падение (prone: штраф на атаки, лишние ходы на встать); толчок не наносит урон напрямую, урон только через террейн (вода/огонь/яма) и столкновения с мебелью.
- Глаголы-примитивы: push | shove | throw | grab | block | distract | threaten | trade | trip; LLM переводит свободную фразу в закрытый список, валидатор проверяет существование цели, соседство, диапазон force; фраза вне списка → ближайший примитив и честный результат.
- Двухуровневая генерация: горячий путь (меню/клавиши → команды без модели, мгновенно), холодный путь (нестандартная фраза → LLM → валидатор → одна повторная попытка со списком обязательных операндов → уход в меню). Trace команд = каноническая история сессии: из него сюжетная память, сейв и воспроизведение.
- Версия ISA пишется в сохранение (иначе добавление opcode ломает старые сейвы); свободные действия логируются так же, как удары.
- Модель под машину игрока 16 GB RAM / 4 GB vRAM: 10B не нужен. 3–4B Q4_K_M (~2.2–2.6 GB) целиком в vRAM, 25–40 tok/s — генератор команд; 7B Q4_K_M (~4.0–4.3 GB) впритык (KV q8_0, ctx 2k, часть слоёв на CPU) 12–20 tok/s — асинхронный нарратив; 10B Q4 (~5.5–6.5 GB) только с расслоением GPU/CPU, 8–15 tok/s, и только асинхронно.
- KV-кэш: ~65 KB/токен в q8_0 при 32 слоях и 8 KV-головах → 2k контекста ≈ 130 MB, 4k ≈ 260 MB; вычислительные буферы ещё 0.4–0.5 GB.
- Контекст 2–3k токенов, не история диалога: стабильный префикс (список opcode'ов + правила + сеттинг) 400–600 токенов байт-в-байт ради переиспользования KV (3–5× скорости), вход ~1.5–2k, выход 100–200 токенов; факты подаются top-k под запрос, никогда вся история.
- Grammar-constrained decoding (GBNF в llama.cpp) снимает большую часть отказов валидации и сокращает вывод до 20–60 токенов.
- Рантатив модели вне кодовой базы игры: отдельный процесс с OpenAI-совместимым HTTP на 127.0.0.1 — llama-server из llama.cpp (MIT) или KoboldCpp; llama-swap для смены модели (4B команды / 7B текст); vLLM не для 4 GB vRAM; файл грамматики ISA — данные рядом с моделью; веса и рантайм не в репозитории (размер + лицензия: Qwen Apache, Llama отдельная лицензия, Gemma свои условия).
- Игра при старте поднимает рантайм (путь к .gguf, число слоёв на GPU, ctx), делает health-check на localhost, при отсутствии ответа переходит в режим без модели: команды из меню + шаблоны нарратива; модель держится resident (загрузка 5–20 с); на Windows общение через localhost HTTP, не через pipe'ы; два клиента с одним интерфейсом (локальный сервер / удалённый API).
- Сценарий по шаблону: 5 актов × 3–5 слотов квестов × 8 вариантов слота = 8^20 ≈ 1.15e18 сочетаний; валидность обеспечивают ограничения (единая тема акта, twist не повторяется в акте, ≥1 квест на каждую ось награды, монотонная кривая силы, boss_gate = f(accumulated_power)); выбор вариантов — constraint-солвер в коде, при неразрешимости seed меняется.
- Бюджет 8 часов: комната ~1.5 мин, квест (переход + комната + диалог + лут) ~25 мин, босс акта ~15 мин → 20 квестов + 5 боссов ≈ 8.3 ч; разброс 3–5 квестов на акт = 6–10 ч; переходы между комнатами — половина времени.
- Гейт готовности акта: ожидаемый power score из статов босса, сравнение в коде; ниже порога → вставка квеста из резервного пула того же акта, пул исчерпан → XP-множитель на последнем квесте; лимит 2 вставки на акт; готовность показывается игроку до босса (например 72%).
- Лут: оси сила / ловкость / магия / защита / скорость / социальное, предмет имеет tag оси + tier 0–3; гарантированный дроп покрывает каждую ось акта, редкие синергии-пары низкой вероятности → рабочий билд всегда собран, «максимально крутой» остаётся случайностью; крафт и конструктор магии = детерминированный путь к любому билду; потолок power предмета по tier акта.
- Цепочка квестов акта фиксируется при начале акта, комнаты/props/враги/реплики — лениво; чекпоинты на границе акта, потому что perma-death на 8-часовом руне слишком жёсткая.
- Мультиплеер: один общий мир (журнал событий) + независимые часы хода у каждого игрока; у каждого opcode есть scope: room | player | world | remote, удалённое воздействие разрешено только в remote-опкодах (pray, gift, say-remote).
- Конфликт только внутри комнаты: room-токен, round-robin; свободные действия (say, look, examine) не расходуют общий ход; таймаут молчания N секунд отдаёт ходы второму игроку; при разделении игроков конфликт исчезает.
- Сходимость без глобального замка: логическое время (счётчик игрока + id игрока), сортировка событий по (logical time, player id), dedupe по id → идемпотентность и сходимость всех клиентов; молитва в городе применяется в мире сразу, пещера получает push, при недоставке событие применяется на следующем ходе.
- Сюжет на пати: одна цепочка актов/квестов, гейт босса по суммарной силе, личные факты игроков отдельно; наррация одна на комнату, не на игрока; практический предел 2–6 игроков.
- Офлайн: часы офлайн-игрока стоят, чужие воздействия применяются к его состоянию как факты и видны при возвращении.
- Смерть в пати: событие `die` → труп как prop-сущность в комнате (блокирует движение, разлагается за T), душа как факт в храме бога игрока, счётчик ходов умершего стоит, room-токен его исключает из очереди.
- Два пути возрождения: подтверждение самим игроком (возрождение в храме ближайшего города; штраф — доля XP, часть лута остаётся у трупа, слабость на N ходов) или партнёр с ресурсом (сквозу возрождения, подношение/золото, примитив revive в конструкторе магии, перенос трупа в храм с весом N). Валидирует код; LLM только формулирует условия бога из фактов сеттинга.
- Штраф смерти не должен ронять гейт акта: падение power ниже boss_gate обрабатывается механизмом вставки доп. квеста; стоимость возрождения эскалирует при повторных смертах в руне (счётчик в фактах).
- Труп — объект мира с последствиями по правилам: партнёр может тащить или закопать (ритуал → другое правило возрождения), монстры могут разграбить или уничтожить → путь через храм становится единственным; душу можно переносить в урне → возрождение там, где урна.
- Города и храмы — постоянные якоря мира, генерируются заранее, не лениво: храм должен существовать до смерти; ближайший храм считается кодом по графу мира.
- Таймаут: если умерший не подтверждает возрождение, через T минут авто-возрождение в храме со штрафом, чтобы пати не блокировалась; если оба мертвы в одной комнате → авто-возрождение обоих со штрафом.
- Призрачная форма: пока возрождение не подтверждено, игрок играет призраком — scope только world|remote (разведка, разговоры с духами, подсказки партнёру), room-глаголы запрещены; альтернативы — possession союзного монстра/питомца, haunting лагеря.
- Смерть как сюжетный факт: долг перед богом, гнев божества, изменение attitudes фракций пишется в базу фактов и влияет на цепочку актов; решение о штрафах и гейтах только в коде.
- Режимы делят одну модель мира (страны, города, храмы, боги, боссы, фракции, шаблоны планов); различается только слой-драйвер: adventure = цепочка фактов → квестовый граф + гейты акта, sandbox = тот же мир без цепочки и без гейтов.
- Sandbox: бесконечное исследование, персонажи игроков не балансируются; вместо гейтов источник сложности — fixed stats по архетипу босса + tiers сложности региона + опциональный scaling босса по power игрока.
- Бесконечный мир: скелет регионов по (координата + seed) с стабильными id (тип, биом, фракция, boss id), полный layout генерируется и хранится только при первом посещении; иначе память растёт линейно с исследованием.
- Присоединение к чужой песочнице: host держит мир и журнал событий, гость подключается к тому же seed + журналу, его команды валидирует host; песочница сохраняется как snapshot + журнал, чтобы друг мог присоединиться/возобновить без online-host.
- В песочнице нет вставки доп. квеста и XP-гейта: штрафы смерти остаются, но не привязаны к boss_gate; room-токен, scope room|player|world|remote и правила возрождения те же.
- LLM в песочнице: локальные истории и слухи региона, микроквесты, которые предлагают NPC по запросу (не глобальная цепочка), реакции богов и фракций на действия игроков; факты накапливаются, поэтому мир помнит последствия — это и есть источник интереса вместо сюжета.
- Персонажи режимов separate: unbalanced sandbox-персонаж ломает гейты акта, поэтому перенос между режимами не делается (или только в sandbox с включёнными гейтами как отдельный hardcore-режим).
- Sandbox полезен как dev/test-режим: проверка механик, ISA, возрождения и пати без генерации сюжета.
- Богатство мира = плотность именованных сущностей и перекрёстных связей (страны, города, храмы, боссы, фракции, реликвии, NPC), а не размер карты; целевая плотность на регион сопоставима с Skyrim.
- World bible как данные (боги: домен, характер, требования, реликвии; страны/холды: законы, продукты, фракции; города: районы, именованные NPC; landmarks; boss roster) — генерируется один раз на создании мира offline-проходом (можно bigger model, минуты), валидируется и сохраняется; в рантайме лениво материализуются только посещённые регионы.
- Двухфазная генерация мира: фаза создания (bible + скелет регионов + chronicle) и фаза рантайма (материализация посещённого); anchors — города, храмы, landmarks, логовы боссов — материализуются всегда, не лениво.
- Chronicle: предистория мира (несколько сотен событий до старта игрока — войны, падения, расколы религий) пишется в базу фактов; руины и надписи — физические следы этих событий (template ruins), история читается из фактов при посещении, не из авторского текста.
- Лор-предметы (книги, надписи, хроники) = проекции фактов в текст; поэтому лор остаётся согласованным с событиями: сожжённый храм в книге описан сожжённым, запись имеет логическое время.
- Дороги как рёбра графа с именованными waypoints; время перехода в игровых часах питает world-тики, поэтому дальний travel двигает жизнь мира.
- Путь к богу: shrine как постоянный anchor в городе → требования бога как факты (relic, attitude ≥ порог, worship, чистота) → ritual → пороговая комната (template threshold) → домен бога (template divine realm, генерируется один раз и сохраняется). Фрагменты маршрута находятся как факты: книга, надпись, слух NPC, награда квеста; маршрут компилируется в исполнимую последовательность регионов/дверей.
- Бог — сущность с attitude и характером: LLM играет бога в диалоге, код валидирует, что бог может дать (blessing, relic, curse) и отказывает при невыполненных требованиях; curse/displeasure пишутся в факты как события.
- Распорядок NPC в городах = те же cheap processes, что и жизнь мира (день: рынок, ночь: таверна), несколько вычислений на тик, без симуляции каждого существа.
- Уникальные квесты строятся из anchors + chronicle (Daedric-паттерн: найти shrine, собрать фрагменты пути, выполнить условие бога), повторяемые — из motive→facts→шаблон (radiant-паттерн).
- Canon vs random world: канон как базовый слой (пантеон, холды, фракции, anchors, регистр речи) даёт learnability, согласованный лор, дешёвый рантайм (stable prefix + KV reuse) и находимость пути к богу; случайный мир даёт новизну ценой связности и upfront-работы.
- Разделение canon/random: anchors, пантеон, холды, фракции, chronicle = канон; filler-регионы между anchors, выбор квестов из motive-разбора, loot, исходы живых процессов и цепочка актов = случайность забега.
- Exhaustion канона митигируется: несколько канонов как выбор при старте, опция создания нового мира offline-проходом, дополнения канона только additive (никаких правок существующих фактов).
- Метрика сравнения: богатство на час игры выигрывает канон, новизна на час — случайный мир, но с потерей связности и повторной генерацией тон-префикса.
- Canon как read-only артефакт с version id, компилируется один раз; забег не mutate канон, version id канона пишется в сейв рядом с версией ISA.
- Тон канона распространяется через constraint-таблицы при компиляции: id богов, id фракций, граф враждебности, карта состояний мест, таблица имён/эпитетов, taboo list; валидатор отвергает id вне канона.
- Canon digest = стабильный префикс 400–600 токенов (пантеон, холды, тон, taboo) в начале контекста; переиспользуется KV, поэтому тон дешёв на каждой генерации.
- Motive-таблица quest generation: loss/greed/faith/fear/revenge/curiosity; NPC разбирает факты региона (loss → украденное, revenge → убийца, faith → храм в плохом состоянии) и генерирует квест из фактов, а не из текста.
- Шаблон квеста со слотами: objective-примитив (retrieve/deliver/clear/scout/bury/pray/negotiate/escort/restore) + target-selector из фактов + twist + оси награды (xp, loot, attitude faction, money, info); reward берётся из реальных ресурсов NPC.
- Валидатор квеста проверяет исполнимость: target существует, достижим, reward в диапазоне, событие не противоречит флагам; неразрешённая дельта отбрасывает квест, LLM даёт flavor или выбор из 3 предвычисленных кандидатов.
- Ledger квестов хранит тройки motive/objective/target; cooldown на NPC и лимит активных квестов на пати; выполнение пишет факты, которые рождают новые motives — цепочки без сюжетной линии.
- World tick: живые процессы как данные (id, scope, precondition, effect delta, rate, probability); тик выбирает eligible процессы, seeded RNG, ≤3 дельты за тик, стоимость O(число процессов), без симуляции существ.
- Permanence rule: state меняется только явной дельтой; сожжённый храм остаётся сожжённым до конца забега, чинится только процессом rebuild с предcondition'ами.
- World-тики считает только host; офлайн catch-up ограничен K тиками, остальные помечаются skipped; результаты событий сохраняются в базе фактов.
